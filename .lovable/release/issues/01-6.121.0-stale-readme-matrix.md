# Release Issue RCA: Stale Version Matrix in readme.md

- **Target Release Version**: `6.121.0`
- **Immediate Previous Version**: `6.120.0`
- **Stale Version Found**: `6.111.0`
- **Step that failed**: Step 3 (Pin the new version in `readme.md`)
- **Files involved**: `readme.md`

## Root Cause Analysis
During the release of `v6.121.0`, the agent used a strict string replacement targeting only the immediate previous version (`6.120.0` -> `6.121.0`). 
However, due to sloppy release cycles in the past, the install snippets and version matrix inside `readme.md` had fallen wildly out of sync and were still hardcoded to `6.111.0`. Because `6.111.0` did not match `6.120.0`, the string replacer silently skipped these 16 occurrences, leaving the installation documentation pointing to an obsolete, broken payload.

The core assumption that "the codebase is perfectly synchronized prior to this release" was flawed. 

## Preventative Measures & Hard Rules
To guarantee this NEVER happens again, the agent's memory and execution protocol have been updated with the following unbendable rules:

1. **Regex-Based Extermination**: When rewriting the `readme.md`, agents MUST NOT rely solely on finding the immediate previous version. They MUST scan for **any** legacy SemVer strings belonging to this major/minor band (e.g., regex `\b[vV]?6\.\d+\.\d+\b`) within badges, install snippets, and version matrices. 
2. **Post-Rewrite Audit**: After rewriting the `readme.md`, agents MUST run a validation search (e.g., `rg "\b6\.\d+\.\d+\b" readme.md | grep -v 6.121.0`) to prove unequivocally that no stale versions remain.
3. **No Blind Trust**: Never assume previous agents updated the install snippets correctly. Check them explicitly.

## Resolution
Manually located all 16 occurrences of `6.111.0` in `readme.md` via `Select-String` and overwrote them to `6.121.0`. Amended the release commit.
